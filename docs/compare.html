和其他方案对比

让 AI agent 用浏览器的方案很多，2026 年又多了一批能连你现有 Chrome 的工具。这一页把它们放在一起按事实对比： 能实测的写实测数字，别家的情况以对方官方文档为准，测不了的不硬写。

各方案现状核对于 2026-10-27（官方 README、文档、发布记录）。下方 ego 和 browser-relay 两节的实测是 2026-07 做的，已注明。

一句话

chrome-use 让任意 AI agent 用你正在用的 Chrome：通过商店扩展和原生消息连接，不开远程调试端口，不用换浏览器。 Claude Code、Codex、Cursor 这类能跑 shell 的 agent 用 CLI，只能接 MCP 的客户端用 MCP；不开终端时，也可以在 Chrome 侧栏或手机上直接跟本机 agent 对话。 多个 agent 各用各的标签组，连真实 Chrome 时不往页面注入补丁。

隐身：连上真实 Chrome 之后还差什么

凡是驱动你真实 Chrome 的方案，浏览器指纹都是真的，这一点各家一样。网站还能从自动化本身留下的痕迹和操作行为里认出 agent， 差别在这里。chrome-use 把这部分当核心能力来做：

  • 不往页面注入补丁：连真实 Chrome 时注入的 JS 补丁数量为零，CreepJS 测不出覆盖痕迹。
  • 默认不开 Runtime.enable：活跃的 Runtime 域是可被检测的 CDP 信号，只有你主动要 console / 错误捕获时才打开。
  • 不在 DOM 里留标记：定位和观察都用节点句柄，不写临时属性，页面的 MutationObserver 看不到。
  • --humanize 行为模拟：曲线鼠标轨迹、元素内落点、可变打字节奏；遇到 Akamai、PerimeterX、DataDome 的页面自动启用。
  • 验证码：普通易盾拼图用 solve-slider，可读的图标点选由 agent 看图操作，失败再交给你；Cloudflare 通过一次后复用 cf_clearance。
  • 需要独立浏览器时：--launch 用原生覆盖（navigator.webdriver、时区、WebRTC 等），不靠可被反查的 JS getter。

我们自测（连真实 Chrome）：CreepJS 0% bot、0% headless；bot.incolumitas、sannysoft、BrowserScan 全部通过，2026-10-27 起 rebrowser-bot-detector 新加的弹窗、绑定全局函数、文档拦截检测也通过（1.5.269）。要注意：第三方 2026 年的测试发现，有头模式下这类指纹检测页已经很难区分不同工具，连原版 Playwright 都能过；真正拉开差距的是行为检测和运行环境（机器、GPU、IP）。chrome-use 跑在你自己的电脑上，环境这一项天然是真的。测试条件见反检测与隐身。 这是特定环境下的测量，不保证不被检测或账号不被封。表里其他方案的文档没有讲这些点，我们也没有逐个实测它们，所以不下结论。

按连接方式分

🧩 扩展连你正在用的 Chrome

chrome-use · OpenCLI · Playwright 扩展 · Claude in Chrome · browser-relay

不打开远程调试，权限走扩展。差别在谁能用（Claude in Chrome 只给 Claude）、怎么装（browser-relay 要开发者模式），以及多 agent、侧栏对话、站点适配器这些上层功能。

🔓 远程调试开关连现有 Chrome

Chrome DevTools MCP · agent-browser · browser-harness · playwright-cli --cdp

Chrome 144 起可以在 chrome://inspect 打开远程调试，再在弹窗里允许。打开后这个 profile 的所有窗口都对工具开放，适合调试和短时任务。

🧭 换一个浏览器

ego(lite) · Comet

装一个新浏览器，导入或重新登录。隔离干净，代价是要换浏览器。

🧰 自动化框架

Playwright · Puppeteer · Selenium · browser-use · Stagehand

写代码驱动受控浏览器。成熟、跨语言，适合测试和固定流程；用你的登录态要另外处理。

☁️ 云端浏览器

Browserbase · Steel · Hyperbrowser · Browser Use Cloud

适合无状态、大规模并发。按小时付费，登录态自己注入，用不上本机的真实会话。

💬 浏览器内置 agent

Gemini in Chrome · ChatGPT 扩展 · Comet

面向终端用户，跟厂商自己的助手对话，你的 Claude Code、Codex 用不上。

反超的一项：单次成型脚本（chrome-use script）

ego 的核心卖点是 “code base, not CLI base”：写一段 JS 把整个任务一次跑完。这一项我们已 ship 并反超： chrome-use script 同样写一段 JS（ego 原样 idiom），用 cu.snapshot/eval/click/fill/find/waitFor/extract 直接驱动，带控制流，一次往返返回结构化结果；JSON op-list 形式亦可（可 dry-run、可机器生成）。

反超点在引擎位置：JS 引擎跑在守护进程里、不在页面里，扛得住硬跳转， 而多页翻页正是 ego 赢、页面内运行时输的地方。实测 HN 翻 3 页收集 ≥100 分故事 = 一次 tool call（旧 per-verb 要 13+）， 跑在你已登录的真 Chrome + 隐身传输，macOS / Linux / Windows 都能用。 用法与两种写法详见 单次成型脚本。

我们从 ego(lite) 学到 & 已搬的

逐项试用对比后，把真缺口用 chrome-use 原生的方式搬过来（进度在 issue #89）：

  • 所有权 + 交接（已实现）：session handoff/resume/status/list，交接给用户后 agent 对该会话的驱动命令全被拒绝。这是逃生口，留给 agent 真做不了的一步（比如解不了的验证码）；不改变自主登录，默认 agent 自己登录、自己驱动，零影响。
  • 富文本 write-probe 纪律（已搬）：见 Canvas / WebGL 页末。
  • 登录继承 / 隔离上下文 / 按名复用 / token 经济（已具备）：relay 天然带登录、每会话标签组隔离、session list、--session-name、更省 token。
  • 定位（locating）（持平）：@ref（backendNodeId 跨调用稳定）+ CSS + XPath + 坐标 + 语义 find role button --name + box 几何 + -s 作用域，对齐 ego 的 loc= / @N。
  • 群组（groups）（持平）：每个 --session 一个彩色 Chrome 标签组、group-scoped 隔离（#40）、多 agent 互不串、只拥有自己建的标签。等价 ego 的 Task Space，只是发生在你的真 Chrome 里，不用换浏览器。

另一个近亲：browser-relay

browser-relay（@linsoai/browser-relay，MIT；最新 1.5.4，2026-09-17 之后没有更新）架构上和我们几乎是同一个思路： 扩展 + 本地 relay 驱动你真实已登录的 Chrome，走 chrome.debugger / CDP，本地绑 127.0.0.1， 提供 CLI + MCP + HTTP，快照带交互元素标注，不开新浏览器、不用一次性 profile。核心理念持平。差异在这几处：

维度browser-relaychrome-use
跨机远程Remote Relay：浏览器往外连公共/自建（Cloudflare）relay，Device ID 鉴权，从另一台机器驱动CLI 只连本机（127.0.0.1 relay）；侧栏对话可以用手机遥控（Tailscale / Cloudflare 隧道 / 局域网）
安装npm 全局 + 开发者模式加载解压扩展（不走商店，不自动更新）一条 curl … | sh + Web Store 一键「添加至 Chrome」
调试横幅会显示；靠 10 分钟空闲自动解绑缓解，或用 --silent-debugger-extension-api 启动（削弱所有 debugger 扩展的安全防护）默认只 attach agent 自己的标签，你的标签不弹横幅；侧栏对话借用你的标签时才显示，收回即消失；无安全折衷
隐身 / 反检测非重点核心能力：CreepJS 0% bot、--humanize 过行为检测、--launch 原生覆盖
多 agent按 --tab id 定位，无会话隔离模型每 --session 一个彩色标签组，多 agent 互不串
复杂多步逐条 verb + eval + stdin单次成型脚本：值总线 + 循环 + 断言，一次往返
定位CSS 选择器 + 快照标注AX 树 @ref（backendNodeId 稳定）+ 语义 find role/name + --heal
运行时Node（npm 包 + launchd/systemd 服务）单一 Rust 二进制，无需 Node，macOS/Linux/Windows

为什么这里没有性能 / token 实测表（不像上面 ego 那节）：两者是同一个机制——扩展 → relay → CDP 驱动同一个真 Chrome， 原始浏览器操作两边必然一样快（都受页面加载 + CDP 限制），性能不构成差异，唯一能差的只有 CLI 启动开销（我们 Rust 二进制 vs 它 Node 起进程）和我们的 batch/script。token 上，我们默认 snapshot -i 是交互树（AX，只列可交互元素）、它是整页标注文本，按 ego 的经验多半我们更省——但要拿确切字节数得把它的 chrome.debugger 扩展装进你的真 Chrome，而同一个标签只能有一个 debugger 客户端，会和 chrome-use 直接冲突。本页纪律是能测才写数字，测不了就不硬写，所以这里只做定性对照。

ℹ️ 诚实结论
browser-relay 在从另一台机器用 CLI 驱动上确实领先（我们的 CLI 只连本机，远程只有手机遥控侧栏对话）。其余维度——一键商店安装、无调试横幅、隐身/humanize、多 agent 隔离、单次成型脚本、AX 树定位、无 Node 单二进制——是 chrome-use 更强。两者血统不同：browser-relay 源自 openclaw-browser-relay，chrome-use 源自 vercel-labs/agent-browser。

对比 workflow

这一页是活文档。每评估一个方案，走同一套流程，保证对比诚实、可复现：

  1. 试用：同一个真实任务，两边各跑一遍，记录命令、结果、耗时、token。
  2. 对比：判断「已有」「持平」还是「真缺口」；持平就如实标注，不硬搬。
  3. 搬：真缺口用 chrome-use 原生方式实现（守住护城河），回填 issue #89 并更新本页。
✅ 原则
只搬能在你的真 Chrome 里实现的优点。任何要求「装一个新浏览器」的路径都不搬，那正是我们的护城河。
