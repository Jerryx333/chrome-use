Getting Started

How chrome-use compares

There are many ways to give an AI agent a browser, and 2026 brought a new wave of tools that attach to the Chrome you already use. This page puts them side by side on the facts: our own measurements where we could run them, the other projects' official docs for everything else, and no numbers we couldn't measure.

Checked against each project's README, docs and releases on 2026-10-27. The ego section was re-measured on 2026-10-27 with current releases of both; the browser-relay comparison dates from 2026-07 and says so.

In one sentence

chrome-use lets any AI agent use the Chrome you're already using: it connects through a Web Store extension and native messaging, with no remote-debugging port and no new browser. Agents that can run a shell (Claude Code, Codex, Cursor) use the CLI, MCP-only clients use the MCP server, and without a terminal you can chat with a local agent in Chrome's side panel or from your phone. Each agent gets its own tab group, and nothing is injected into pages when driving your real Chrome.

Stealth: what's left once you're on a real Chrome

Any tool that drives your real Chrome presents a genuine fingerprint; that part is the same everywhere. Sites can still spot an agent from traces the automation leaves and from how it behaves, and that's where tools differ. chrome-use treats this as a core capability:

  • Nothing injected: zero JS patches when driving your real Chrome, so CreepJS finds no overrides.
  • Runtime.enable off by default: an active Runtime domain is a detectable CDP signal; it's only turned on when you ask for console or error capture.
  • No marks in the DOM: locating and observing use node handles instead of temporary attributes, so page MutationObservers see nothing.
  • --humanize: curved mouse paths, in-element landing points and variable typing rhythm, switched on automatically on Akamai, PerimeterX and DataDome pages.
  • CAPTCHAs: solve-slider for ordinary Yidun puzzles, screenshot-guided clicks for readable icon challenges, then a handoff to you if it fails; a Cloudflare cf_clearance is reused once earned.
  • When you need a separate browser: --launch uses native overrides (navigator.webdriver, timezone, WebRTC and more) instead of JS getters that can be detected.

Our own runs on a real Chrome: CreepJS 0% bot and 0% headless; bot.incolumitas, sannysoft and BrowserScan all pass, and since 1.5.269 so do rebrowser-bot-detector's new popup, binding-global and document-interception checks (added 2026-10-17/19). Keep in mind that independent 2026 tests found these fingerprint pages barely separate tools in headed mode (even plain Playwright passes); behavior checks and the environment (machine, GPU, IP) are what separate them. chrome-use runs on your own computer, so the environment is genuine by construction. Test conditions are in Stealth & Anti-detection. These are measurements in a particular environment, not a promise of invisibility or account safety. The other tools' docs don't cover these points and we haven't benchmarked them, so we draw no conclusion about them.

By how they connect

🧩 An extension in the Chrome you use

chrome-use · OpenCLI · Playwright extension · Claude in Chrome · browser-relay

No remote debugging; permissions go through the extension. The differences are who can use it (Claude in Chrome is Claude-only), how it installs (browser-relay needs Developer mode), and what sits on top: multi-agent tab groups, side-panel chat, site adapters.

🔓 The remote-debugging toggle

Chrome DevTools MCP · agent-browser · browser-harness · playwright-cli --cdp

Since Chrome 144 you can enable remote debugging at chrome://inspect and allow it in a dialog. Once on, every window of that profile is open to the tool, which suits debugging and short tasks.

🧭 Switch browsers

ego(lite) · Comet

Install a new browser and import or sign in again. Clean isolation, at the cost of changing browsers.

🧰 Automation frameworks

Playwright · Puppeteer · Selenium · browser-use · Stagehand

Drive a controlled browser from code. Mature and cross-language, good for tests and fixed flows; your sign-ins need separate handling.

☁️ Cloud browsers

Browserbase · Steel · Hyperbrowser · Browser Use Cloud

For stateless, high-concurrency work. Pay by the hour, inject sign-ins yourself; your local sessions don't come along.

💬 Built-in browser agents

Gemini in Chrome · ChatGPT extension · Comet

For end users chatting with the vendor's assistant. Your Claude Code or Codex can't use them.

chrome-use vs ego(lite): measured in 2026-10

ego(lite) is positioned close to us: both let agents use real sign-ins without fighting for your tabs. On 2026-10-27 we re-ran the comparison on one machine (190, M4) with current releases: chrome-use 1.5.269 (Chrome 155, headed --launch) and ego(lite) 0.6.1.13 (Chromium 156, ego-browser skill 2.1.0). Each number is the median of 5 interleaved rounds. Both conclusions from the July run no longer hold; these are the new results.

Single-pass scripting (chrome-use script)

ego's core pitch is “code base, not CLI base”: write one JS program that runs the whole task in one pass. chrome-use has the same style: chrome-use script runs a real JS program (ego's exact idiom) driving the page via cu.snapshot/eval/click/fill/find/waitFor/extract, with control flow, returning structured results in one round-trip; a JSON op-list form is also available (dry-runnable, machine-generatable).

The JS engine lives in the daemon, not the page, so it survives hard navigations and suits multi-page flows. Measured: crawl 3 HN pages collecting every ≥100-point story = one tool call (the old per-verb way needs 13+), on your already-logged-in real Chrome over the stealth transport, on macOS, Linux and Windows. Full usage and both forms on Single-pass Scripting.

What we learned from ego(lite) & ported

After trialing each item, we ported the real gaps the chrome-use way (progress in issue #89):

  • Ownership + handoff — implemented session handoff/resume/status/list: once handed off, every browser-driving command on that session is refused. It's an escape hatch for the rare step the agent truly can't do (e.g. an unsolvable captcha) — it does not change autonomous login; by default the agent logs in and drives itself, zero-impact.
  • Rich-editor write-probe discipline — ported (see the end of Canvas / WebGL).
  • Login inheritance / isolated contexts / reuse-by-name / token economy — already covered (relay carries logins, per-session tab groups, session list, --session-name; tokens are compared in the measured table above).
  • Locating — covered · parity: @ref (backendNodeId-stable across calls) + CSS + XPath + coordinates + semantic find role button --name + box geometry + -s scoping, matching ego's loc= / @N.
  • Groups — covered · parity: each --session maps to a colored Chrome tab group, group-scoped isolation (#40), agents never cross tabs, a session owns only the tabs it created — equivalent to ego's Task Space, except it happens in your real Chrome instead of a separate browser.

Another close cousin: browser-relay

browser-relay (@linsoai/browser-relay, MIT; latest 1.5.4, no updates since 2026-09-17) is architecturally almost the same idea as us: an extension + local relay driving your real, logged-in Chrome over chrome.debugger / CDP, bound to 127.0.0.1, exposed via CLI + MCP + HTTP, with snapshots annotating interactive elements — no new browser, no throwaway profile. Why there's no measured perf / token table here (unlike the ego section above): the two are the same mechanism — extension → relay → CDP driving the same real Chrome, so raw browser operations are necessarily equally fast (both bound by page load + CDP). Performance isn't a differentiator; the only real deltas are CLI startup (our Rust binary vs its Node process) and our batch / script. On tokens, our default snapshot -i is an interactive AX tree (interactive elements only) while theirs is annotated full-page text, so by the ego experience we're likely leaner — but getting exact byte counts would mean installing its chrome.debugger extension into your real Chrome, and a tab can have only one debugger client, so it conflicts head-on with chrome-use. This page's rule is measure or don't claim a number, so this comparison stays qualitative.

ℹ️ Honest verdict
browser-relay is genuinely ahead on driving the CLI from another machine (our CLI connects locally only; remote use is limited to driving side-panel chat from a phone). On the rest — one-click store install, no debug banner, stealth/humanize, multi-agent isolation, single-pass scripting, AX-tree locating, a Node-free single binary — chrome-use is stronger. Different lineage too: browser-relay descends from openclaw-browser-relay, chrome-use from vercel-labs/agent-browser.

The comparison workflow

This page is a living document. For every tool we evaluate, the same loop keeps the comparison honest and reproducible:

  1. Trial — the same real task on both; record commands, result, time, tokens.
  2. Compare — "already have it," "at parity," or "real gap"; if parity, say so — don't force-port.
  3. Port — for a real gap, implement it the chrome-use-native way (keep the zero-install moat), update issue #89 and this page.
✅ The principle
Only port advantages we can deliver inside your real Chrome. Any path that requires installing a new browser is a non-port — that's exactly our moat.
