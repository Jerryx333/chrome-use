What Agents Can Do

Canvas / WebGL / Games

Games, maps, 3D viewers and design canvases like Figma are drawn on a <canvas>, so the page structure has no buttons to click. Your agent drives them by looking at the picture and clicking or pressing keys at coordinates, and reads engine state directly when it can.

Ask your agent

In this browser game, hold D to walk right and jump over the first gap.

Hold durations are timed inside chrome-use, which is steadier than one command per key.

Export what's on this Figma canvas right now as a PNG.

You get the rendered picture, not the design source.

Add a paragraph of meeting notes at the end of this Google Doc.

It types a probe word first to confirm the cursor is in the body, then the text.

What the agent does

  1. It first checks with snapshot -i and get text --pierce that there really is nothing clickable; if it gets refs, it doesn't use coordinates.
  2. It looks with canvas capture or screenshot, works out the position, then click x y; held keys use press --hold.
  3. A fixed timed sequence goes out in one batch; real-time control uses stream, receiving frames and sending input over a WebSocket.
  4. When a game engine exposes its state on a page global, eval reads position or score directly instead of guessing from a screenshot.
  5. In editors like Google Docs or Notion it types a probe word to confirm where input lands, then the real text, then checks with a screenshot or export.

What you'll see

  • When working in your Chrome through the extension, coordinate clicks can land on your foreground tab. For tasks with many coordinate actions the agent should prefer a browser it launches itself (--launch) or its own tabs, or confirm state through the app's backend.
  • canvas capture returns the rendered picture. Design source files and hidden game state come from the app's own API.
  • Before reporting done, the agent should have read the result back with a screenshot, export or API; ask to see the screenshot.
  • At the end the agent runs done: tabs it opened along the way close, and pages you need to see or keep using stay open.

Under the hood

The commands and flags the agent runs. Read on if you write your own scripts, debug a run, or want the details.

Game screens, voice-room mic seats, map tiles, 3D viewers, design canvases (Figma / Modao) — these UIs paint everything onto a <canvas>, with no DOM nodes and no accessibility nodes behind them. snapshot / find / eval querySelector will never get their @ref. This isn't a missing feature — it's a hard limit. This page teaches a different playbook: look at pixels, act by coordinates.

Why canvas has no ref

A <canvas> / WebGL hit area, and a closed shadow root, expose no DOM / AX node for the controls they paint. So no matter how snapshot scans, it cannot fabricate a @ref — coordinates are the only handle. When snapshot detects such a page it prints a hint.

ℹ️ What actually is coordinate-only
Only canvas and closed shadow roots require coordinates. Open shadow roots, and same-origin / cross-origin iframes, are rendered normally by snapshot -i — prefer @ref for those.
⚠️ Coordinate clicks can drift over the relay
Over the extension relay, a coordinate click can land on the user's foreground tab. Before doing a lot of canvas coordinate work, prefer --launch or a tab you own, or bypass the canvas entirely and confirm the real state via the app's backend / API. See Driving real Chrome.

Reading the screen: canvas capture and screenshot

On a canvas page, eval / get text mostly return nothing useful, so looking is your only read path. Enumerate the canvases first, grab the rendered pixels, then let you interpret them:

Read canvas pixels 
# Enumerate the <canvas> elements on the page (size, type)
$ chrome-use canvas list

# Save the canvas "rendered pixels" as PNG — toDataURL gets the full
# backing-store resolution (e.g. Figma's 2522x1904); for WebGL without
# preserveDrawingBuffer / tainted canvases it falls back to screenshot
$ chrome-use canvas capture out.png

# Or just grab a region shot to "see" the current state
$ chrome-use screenshot /tmp/s.png
ℹ️ You get the "rendered result", not the source data
canvas capture grabs the painted picture. Figma's source assets, a game's hidden state, and so on live in the app's binary storage / API, not on the canvas. When you need the source data, go through that app's own interface.

Symptom: text shows in get text, but no @ref

Voice-room mic seats (Zego / Agora), prototype canvases (Modao / modao), game HUDs, and some Web Components paint their controls — so the text appears in get text / read_page (e.g. a string of "Add Add Add…"), but snapshot -i lists nothing and querySelectorAll returns 0. With no addressable node, @ref / find can't reach it. Drive by position:

Rule out closed shadow first, then click by coordinate 
# Try first: if it's just a "closed" shadow root (not canvas),
# this reads through it — cheap, worth trying first
$ chrome-use get text --pierce

# Otherwise "look" for where the control is
$ chrome-use screenshot /tmp/s.png

# Click that pixel (bare numbers = coordinates)
$ chrome-use click <x> <y>

Interact by coordinate: click and press --hold

On canvas, everything runs on coordinates. Compute the target point and click x y directly; when you first need a container's CSS-px box, use box @ref to get its position and convert. Coordinates are the right tool here — the snapshot-first rule explicitly makes this exception for canvas.

Coordinate click and hold-move 
# Interact by viewport coordinates
$ chrome-use click 640 360

# Hold-move with precise timing (timed inside the daemon —
# not keydown + shell-sleep + keyup, which adds ~250ms of
# jitter on every round trip)
$ chrome-use press d --hold 800

# Discrete actions (jump / attack / confirm)
$ chrome-use press Space
✅ press --hold instead of stitching sleeps
For a sustained action use press --hold <ms> — the timing happens inside the daemon, far steadier than a shell-stitched keydown / sleep / keyup. For more keys and input see Interacting.

batch: run a timed sequence in one round trip

Don't drive frame-by-frame with one CLI call per action — that's the slowest, lowest-fidelity approach, since every call is a process launch + round trip. Use batch to pack a timed sequence into a single round trip: it sends each step to the already-running daemon, and press --hold and wait both block inside the daemon, so the timing is accurate.

A timed sequence in one round trip 
$ chrome-use batch "press d --hold 900" "press j" "press j" "wait 200" "press d --hold 500"
🪜 batch is a fixed sequence only
batch steps can't pass values between each other, and there are no loops or conditions — it's a hard-coded run of actions. To decide the next step from the last one, or to loop or branch, use script (values between steps + loops + conditions + assertions, still one round trip); for continuous real-time driving, use the stream WebSocket below. Pick the layer that's just enough.

Read engine globals instead of guessing pixels

Rather than guessing from a screenshot, read the real state directly. eval runs in the page's main world, so for framework / engine-based games you can often reach straight into its global object — a Phaser / PIXI / Three instance, a store, or window.__GAME__ — and read position / score directly, far better than guessing at a screenshot.

Read game state directly 
# eval runs in the main world, so it can read the engine instance on window
$ chrome-use eval "window.__GAME__.player.position"

Real-time driving: the WebSocket stream

For truly real-time driving, drop the CLI entirely and use a WebSocket. chrome-use stream enable opens a bidirectional WS (stream status prints ws://127.0.0.1:<port>). Connect once and you get both a ~60fps live screencast and the ability to send input on the same socket — no per-action process launch, no round trips, and it works across the extension relay.

Open the stream and read its address 
$ chrome-use stream enable
$ chrome-use stream status   # prints ws://127.0.0.1:<port>
node — live frames + locally-timed input 
// node (global WebSocket): live frames + locally-timed input
const ws = new WebSocket("ws://127.0.0.1:PORT")
ws.onmessage = e => { const m = JSON.parse(e.data); if (m.type==="frame") {/* base64 jpeg */} }
const k = (eventType,key,code,vk) => ws.send(JSON.stringify({type:"input_keyboard",eventType,key,code,windowsVirtualKeyCode:vk}))
k("keyDown"," ","Space",32); setTimeout(()=>k("keyUp"," ","Space",32), 80)   // one jump
// mouse works the same: {type:"input_mouse",eventType:"mousePressed",x,y,button:"left",clickCount:1}
✅ When to use WS vs a screenshot
It's the difference between "flipping through slides" and "actually playing the game". Leave one-off checks to screenshot; use WS for any sustained real-time control.

Virtualized rich editors: probe before you commit

Unlike canvas, Google Docs/Sheets, Notion, Figma, and Lark/Feishu do have a DOM — but it lies. The editing surface is a virtualized layer, and the DOM around it is littered with decoys: a hidden <textarea> mirror, an offscreen input, a toolbar/search box, a title field. fill / type on a ref plucked from snapshot -i often lands your text in one of those decoys — the title bar, a find box — not the document. Snapshot-first still holds for navigation (menus, buttons, dialogs); but for the main editing surface, prove where your keystrokes go before you commit a paragraph.

write probe → verify → then the real content 
# 1. WRITE PROBE — one throwaway token via real keystrokes, don't dump the payload yet
$ chrome-use click 520 300              # click into the document body by coordinate
$ chrome-use keyboard type "zzprobe"    # real keydown/keypress/keyup, not fill/insertText
# 2. VERIFY it landed in the document — not the title/toolbar/a hidden input
$ chrome-use screenshot /tmp/probe.png  # SEE where "zzprobe" appeared (or read it back via the app's export/API)
# 3a. landed in the doc  → continue with real keystrokes
# 3b. landed in the wrong field → stop using DOM/fill here: click the body by coordinate, real keyboard only
⚠️ Three rules of thumb
Don't trust fill @ref / type @ref for the document surface until a probe proves the target (toolbars, menus, comment boxes, the share dialog are real DOM — @ref is fine; the canvas/grid itself is the trap); prefer real keystrokes (keyboard type / keyboard press) over fill/insertText (virtualized editors listen for key events; insertText silently no-ops or writes to the mirror); verify by readback, not assumption — screenshot or use the app's export/API to confirm the content landed before reporting done.

Decision cheat sheet

📖 Try snapshot first

Not sure it's canvas? Run snapshot -i / get text --pierce first — if you get a @ref, don't use coordinates.
🖱️ Coordinate interaction

click x y, press --hold, batch timed sequences — drive the painted controls.
🎬 Screenshots and recording

screenshot to see state, canvas capture to grab rendered pixels, record the viewport for playback.
